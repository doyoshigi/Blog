# OSI 계층 별 프로토콜(2)
## 1. TELNET과 SSH
### 1.1 원격 터미널 접속이 필요한 이유
리눅스 서버를 구축했을 때 리눅스 서버에 다양한 작업을 진행해야 합니다. 하지만 대부분의 리눅스 서버는 회사의 서버실, 호스팅 업체, 클라우드 등에 위치해 있기 때문에 서버에 물리적, 직접적으로 접근하여 작업을 하는데에 많은 제한이 있습니다.

따라서 원격으로 접속하여 서버 작업을 처리하는 것이 필수적이게 되었습니다.

리눅스 서버에 원격으로 접속하기 위한 방법은 크게 두가지가 있습니다. 하나는 VNC, XRDP, XDMCP와 같은 프로토콜을 사용하여 그래픽 데스크톱 환경으로 접속하는 방법과 그래픽을 띄우지 않고 터미널로 접속하는 Rlogin, Telnet, SSH와 같은 프로토콜이 있습니다.

### 1.2 터미널, 터미널 애뮬레이터
터미널 애뮬레이터란 터미널을 가상으로 구현한 프로그램입니다. 일반 터미널은 컴퓨터와 사용자 간의 소통을 위한 인터페이스에 불과합니다.

Xshell, iTerm 등과 같은 터미널 애뮬레이터는 리눅스 서버로 터미널 접속 프로토콜을 사용하여 접속하는 것을 도와줍니다.

이때 Telnet과 SSH같은 프로토콜을 사용하여 원격으로 리눅스 서버에 접속할 수 있게됩니다.

  
리눅스 시스템 자체에 있는 터미널 클라이언트는 대부분 원격 접속이 아니기 때문에 SSH프로토콜을 사용하지 않습니다.

### 1.3 TELNET(텔넷)이란?
Telnet은 네트워크 상에서 원격 시스템에 접속하여 명령어를 입력하고 실행할 수 있는 프로토콜입니다. 23번 포트를 사용합니다.

초기에 많은 시스템에서 표준으로 사용되었지만 암호화되지 않은 평문 통신을 사용하기 때문에 보안에 취약합니다.

대부분의 유닉스 시스템에서 사용할 수 있으며 실질적으로 모든 플랫폼에서 사용할 수 있습니다.

TCP/IP 스택을 갖춘 네트워크 장비와 운영체제들은 원격 구성(Windows NT 기반)을 위해 몇 가지 종류의 텔넷 서비스 서버를 지원합니다.

### 1.4 SSH(Secure Shell)이란?
SSH는 네트워크를 통해 안전하게 원격 시스템에 접속할 수 있도록 설계된 프로토콜입니다. 22번 포트를 사용합니다.

SSH는 통신 내용이 암호화되어 전송되기 때문에 데이터 도청이나 해킹으로부터 안전합니다. 따라서 보안이 중요한 환경에서 사용됩니다.

최근에는 보안때문에 대부분 SSH 프로토콜을 사용합니다.

### 1.5 TELNET과 SSH의 공통점, 차이점
**공통점**
- 원격으로 PC에 엑세스 하기 위해 사용합니다.

**차이점**

| TELNET   | SSH            |
| -------- | -------------- |
| 23번 포트   | 22번 포트         |
| 통신 암호화 x | 통신 암호화         |
| 본인 인증x   | 본인 인증(공개 키 사용) |
| 보안 오버헤드x | 보안 오버헤드 존재     |
보안적인 부분이 아예없는 Telnet의 단점때문에 현재는 SSH가 거의 모든 용도에서 Telnet을 대처했습니다.

## 2. HTTP와 HTTPS
### 2.1 HTTP(Hyper Text Transfer Protocol)란?
HTTP란 서버/클라이언트 모델을 따라 데이터를 주고 받기 위한 프로토콜입니다. 즉 HTTP는 인터넷에서 하이퍼텍스트를 교환하기 위한 통신 규약이며 80번 포트를 사용합니다.

**HTTP 메시지**
![[Pasted image 20251209215408.png]]

HTTP는 OSI 7 계층에서 애플리케이션 계층 프로토콜로 TCP/IP 위에서 동작합니다. HTTP는 상태를 가지고 있지 않는 Stateless 프로토콜로 요청 메시지는 Method, Path, Version, Headers, Body로 구성되어 있습니다.

![[Pasted image 20251209215419.png]]

또한 응답 메시지는 Version, Status code, Status message, Headers, Body로 구성됩니다.

### 2.2 HTTPS(Hyper Text Transfer Protocol Secure)란?
Hypertext Transfer Protocol over Secure Socket Layer, HTTP over TLS, HTTP over SSL, HTTP Secure 등으로 불리는 HTTPS는 HTTP에 데이터 암호화가 추가된 프로토콜입니다. 443번 포트를 사용합니다.

**대칭키 암호화와 비대칭키 암호화**  
HTTPS는 대칭키 암호화 방식과 비대칭키 암호화 방식을 모두 사용하고 있습니다.

**대칭키 암호화** 방식은 클라이언트와 서버가 동일한 키를 사용해 암호화/복호화를 하는 방식입니다. 연산 속도가 빠르지만 키가 노출되면 위험합니다.

**비대칭키 암호화** 방식은 공개키와 개인키의 1쌍을 가지고 암호화/복호화를 진행합니다. 연산속도가 느리지만 키가 노출되어도 비교적 안전하다는 장점이 있습니다.

이때 공개키는 모두에게 공개가능한 키이고 개인키는 나만 알고 있어야 하는 키를 말합니다.

공개키로 암호화하여 개인키로만 복호화할 수 있게한다면 개인키는 나만 가지고 있기 때문에 나만 볼 수 있는 효과를 냅니다.

그리고 개인키로 암호화하고 공개키로 복호화할 수 있도록 한다면 공개키는 모두에게 공개되어 있기때문에 내가 인증한 정보임을 알려 신뢰성을 보장할 수 있습니다.

**HTTPS 동작과정**  
HTTPS는 대칭키 암호화와 비대칭키 암호화를 모두 사용하여 빠른 연산속도와 안정성을 모두 가져가고 있습니다.

HTTPS 연결과정에서 먼저 서버와 클라이언트가 세션키를 교환하는데 여기서 세션키는 주고 받는 데이터를 암호화하기 위한 대칭키입니다. 빠른 연산 속도가 필요하므로 데이터 교환에서는 세션키를 대칭키로 사용합니다.

여기서 세션키를 클라이언트와 서버가 교환할 때 세션키는 대칭키이므로 안전하게 교환해야할 필요가 있는데 이때 비대칭키가 사용됩니다.

정리하면 처음 연결을 성립하여 안전하게 세션키를 공유하는 과정에서는 비대칭키가 사용되는 것이고, 이후 데이터를 교환하는 과정에서는 빠른 연산 속도를 위해 대칭키가 사용됩니다.

![[Pasted image 20251209215453.png]]![[Pasted image 20251209215529.png]]

위는 세션키를 교환하는 모습을 나타낸 그림입니다.

1. 먼저 클라이언트가 서버로 최초 연결을 시도합니다.
2. 서버는 공개 키(인증서)를 브라우저에 넘겨줍니다.
3. 브라우저는 인증서의 유효성을 검사하고 세션키를 발급합니다.
4. 브라우저는 세션키를 보관하고 서버의 공개키로 세션키를 암호화하여 서버로 전송합니다.
5. 서버는 개인키로 암호화된 세션키를 복호화하여 세션키를 얻습니다.
6. 결과적으로 클라이언트와 서버는 동일한 세션키를 공유하게 되고 데이터를 전달할 때 세션키로 암호화/복호화를 진행할 수 있게 됩니다.

**HTTPS의 발급 과정**  
위에서 살펴봤던 과정에서 서버의 비대칭키는 어떻게 발급되게 될까요?

![[Pasted image 20251209215634.png]]

1. 한 기업에서 HTTPS를 적용하기 위해 공개키/개인키를 발급합니다.
2. CA에게 돈을 지물하고 공개키를 저장하는 인증서의 발급을 요청합니다.
3. CA는 CA 이름, 서버의 공개키, 서버의 정보 등을 기반으로 인증서를 생성하고 CA기업의 개인키로 암호화하여 요청한 기업에 인증서를 제공합니다.
4. 기업은 클라이언트에게 암호화된 인증서를 제공합니다.
5. 브라우저는 CA의 공개키를 미리 다운받아 가지고 있기 때문에 암호화된 인증서를 복호화하여 기업의 공개키를 얻습니다.
6. 얻은 기업의 공개키를 통해 세션키를 공유합니다.

인증서는 CA의 개인키로 암호화되었기 때문에 신뢰성을 확보할 수 있고 클라이언트는 기업의 공개키로 데이터를 암호화해 기업만이 기업의 개인키를 활용하여 데이터를 복호화할 수 있습니다.

![[Pasted image 20251209215647.png]]

브라우저에는 CA들의 정보가 사전에 등록되어 있어 등록되어 있는 CA의 인증서가 아닐경우 위의 사진처럼 브라우저에 나타나게 됩니다.

### 2.3 HTTP, HTTPS
HTTPS와 HTTPS의 차이점은 암호화에 있습니다. HTTP는 암호화하지 않기 때문에 보안에 취약하지만 HTTPS는 암호화하기 때문에 취약하지 않습니다.

하지만 HTTPS는 Handshaking에서의 추가적인 오버헤드와 암호화/복호화 과정이 추가되기에 속도가 느리다는 단점이 있습니다.  
그리고 HTTPS 인증서를 발급하고 유지하는 비용도 발생합니다.

## 3. DNS(Domain Name System)

### 3.1 DNS(Domain Name System)이란?
DNS는 사용자에게 친숙한 도메인 이름(e.g. [www.ibm.com](http://www.ibm.xn--com\)-jy1s/))을 컴퓨터가 네트워크에서 서로를 식별하는 데 사용하는 IP주소로 변환하는 인터넷 표준 프로토콜입니다. application layer에서 구현됩니다.

DNS는 '인터넷 용 전화번호부'라고도 불리는데 DNS의 도메인 이름 관리방식과 스마트폰의 전화번호부 관리방식이 거의 동일하기 때문입니다.

스마트폰에서 별명으로 전화번호를 저장하고 사용자는 해당 전화번호를 외우지 않아도 되는 것처럼 DNS를 사용하면 사용자가 IP주소가 아니라 인터넷 도메인 이름을 사용하여 웹사이트에 연결할 수 있게 됩니다.

### 3.2 DNS 서버 유형
![[Pasted image 20251209215842.png]]

처음부터 개발자들은 빠르게 확장되는 컴퓨터 네트워크에 보조를 맞출 수 있는 도메인 이름 확인에 대한 보다 동적인 접근 방식을 용이하게 하기 위해 계층적 분산 데이터베이스 구조로 DNS를 설계했습니다.

계층 구조는 .(점)으로 표시된 루트 수준에서 시작하여 '.com', '.org', '.net'과 같은 최상위 도메인(Top Level Domain, TLD) 또는 '.uk' 및 '.jp'와 같은 국가 코드 TLD(ccTLD)및 두 번째 수준 도메인으로 나뉩니다.

DNS 아키텍처는 두 가지 유형의 DNS 서버로 나뉩니다. 바로 재귀 서버와 권한 있는 서버입니다. 재귀 DNS 서버는 사용자를 웹 사이트에 연결하는 정보를 검색하는 요청을 수행하는 서버입니다.

**재귀 서버(Local DNS Server)**  
재귀 확인자 또는 DNS 확인자라고도 불리는 재귀 서버는 일반적으로 인터넷 서비스 공급자(ISP), 대기업 또는 기타 타사 DNS 서비스 공급자가 관리합니다. 이들은 최종 사용자를 대신하여 도메인 이름을 IP주소로 변환합니다.

또한 재귀 서버는 특정기간(TTL)동안 해당 쿼리과 IP주소를 캐싱하여 동일한 쿼리가 들어오면 바로 바로 응답할 수 있습니다.

![[Pasted image 20251209215904.png]]

사용자의 브라우저가 재귀 서버에 IP주소를 쿼리하면 재귀 서버는 캐싱 되어 있는 데이터를 확인하고 만약 해당 쿼리가 캐싱되있다면 캐싱된 응답을 캐싱되어 있지 않다면 Root DNS서버에 쿼리하여 IP주소를 찾고 사용자의 브라우저에게 반환하게 됩니다.

**권한 있는 서버**  
권한 있는 서버는 답변을 제공합니다. 권한 있는 이름 서버는 도메인에 대한 최종 레코드를 보유하고 해당 영역 내에 저장된 도메인 이름에 대한 요청에 응답합니다.(일반적으로 도메인 소유자가 구성한 답변으로 응답)

권한 있는 DNS 이름 서버는 여러 유형이 있으며, 각 유형은 DNS 계층 구조 내에서 특정 기능을 수행합니다.

권한 있는 DNS 이름 서버의 종류는 아래와 같습니다.

**Root DNS Server**  
Root DNS Server는 DNS 계층 최상위에 위치하여 루트 영역(DNS의 중앙 데이터베이스) 관리를 담당합니다. 루트 영역 내에 저장된 레코드에 대한 쿼리에 응답하고 적절한 TLD DNS Server로 요청을 참조합니다.

TLD에 대한 요청을 처리하고 쿼리를 적절한 TLD DNS Server로 전달하는 13개의 서로 다룬 루트 서버 네트워크(A~M으로 식별)를 쿼리하는 데 사용되는 13개의 IP주소가 있습니다. 이러한 Root DNS Server 네트워크는 인터넷주소자원관리기구(ICANN)에서 운영합니다.

**TLD DNS Server**  
TLD DNS Server는 일반 최상위 도메인(gTLD)을 비롯한 계층 구조의 다음 수준을 관리하는 역할을 합니다. TLD DNS Server는 해당 TLD 내의 특정 도메인에 대한 권한 있는 이름 서버로 쿼리를 전달합니다. 따라서 ".com"에 대한 TLD DNS Server는 ".com"으로 끝나는 도메인을 디렉션하고, ".gov"에 대한 TLD이름 서버는 ".gov"로 끝나는 도메인을 디렉션합니다.

**Domain Name Server(2단계 도메인 이름 서버, Authoritative DNS Server)**  
도메인 이름 서버는 "ibm.com"과 같이 전체 도메인 이름의 IP 주소가 포함된 영역 파일을 보유합니다.

### 3.3 DNS 작동방식
DNS의 모든 쿼리는 동일한 논리에 따라 IP 주소를 확인합니다.

사용자가 URL을 입력하면 컴퓨터는 DNS 서버를 점진적으로 쿼리하여 사용자의 요청을 처리하는 데 적합한 정보 및 리소스 레코드를 찾습니다. 이 프로세스는 DNS가 해당 도메인과 연결된 권한 있는 DNS 서버에서 올바른 응답을 찾을 때까지 계속됩니다.

1. 쿼리 시작
    - 사용자가 "ibm.com"과 같은 도메인 이름을 브라우저나 앱에 입력하면 요청이 재귀 DNS 확인자로 전송됩니다. 일반적으로 사용자의 디바이스에는 인터넷 서비스 공급자(ISP)가 제공하는 사전 정의된 DNS 설정이 있으며, 이를 통해 클라이언트가 쿼리하는 재귀 확인자를 결정합니다.
2. 재귀 확인자
    - 재귀 확인자는 이전 DNS 조회를 보관하는 웹 브라우저 또는 운영 체제 내의 임시 스토리지인 캐시에서 도메인의 해당 IP주소를 확인합니다. 재귀 확인자의 캐시에 DNS 조회 데이터가 없는 경우 확인자는 루트 서버부터 시작하여 권한 있는 DNS 서버에서 데이터를 검색하는 프로세스를 시작합니다. 재귀 확인자는 최종 IP주소를 찾을 때까지 DNS 계층 구조를 쿼리합니다.
3. Root DNS Server
    - 재귀 확인자는 Root DNS Server에 쿼리하고, Root DNS Server는 해당 도메인에 대한 적절한 TLD DNS Server(이 경우에는 ".com"을 담당하는 TLD DNS Server)에 대해 참조로 응답합니다.
4. TLD DNS Server
    - 확인자는 ".com" TLD DNS Server로 쿼리하고 이 서버는 "ibm.com"에 대한 권한 있는 이름 서버의 주소로 응답합니다. 이 서버를 2단계 도메인 이름 서버라고도 합니다.
5. 도메인 이름 서버(2단계 도메인 이름 서버)
    - 확인자는 도메인 이름 서버에 쿼리하고, 서버는 DNS 영역 파일을 조회하고 제공된 도메인 이름에 대한 IP주소 레코드로 응답합니다.
6. 쿼리 해결
    - 재귀 확인자는 레코드의 TTL에 지정된 시간 동안 DNS 레코드를 캐시하고 IP 주소를 사용자의 디바이스로 반환합니다. 브라우저는 해당 IP주소를 통해 호스트 서버에 대한 연결이 가능합니다.

### 3.4 DNS Record 종류
DNS는 여러 레코드 유형을 사용하여 데이터를 저장할 수 있습니다.

**A 레코드, AAA 레코드**  
A 레코드는 IPv4 주소, AAA 레코드는 IPv6주소에 매핑됩니다.

**MX 레코드(메일 교환기 레코드)**  
MX 레코드는 도메인의 SMTP 이메일 서버를 지정합니다.

**CNAME 레코드(표준이름 레코드)**  
CNAME 레코드는 별칭에서 표준 도메인으로 호스트 이름을 리디렉션합니다.  
예를 들어 "fow.kr"이라는 도메인을 입력하면 "fow.lol"도메인으로 이동하게 됩니다.

**NS 레코드(이름 서버 레코드)**  
NS 레코드는 도메인에 대한 권한 있는 이름 서버를 나타냅니다.

**PTR 레코드(포인터 레코드)**  
PTR 레코드는 역방향 DNS 조회를 지정하며 IP주소를 도메인 이름에 다시 매핑합니다.

**TXT 레코드(텍스트 레코드)**  
TXT 레코드는 이메일 인증을 위한 발신자 정책 프레임워크 레코드를 나타냅니다.

### 3.5 DNS 쿼리 유형
DNS 조회에는 일반적으로 세 가지 유형의 쿼리가 포함됩니다.

**Recursive Query**
![[Pasted image 20251209220134.png]]

재귀 서버와 DNS 클라이언트를 연결하는 Recursive Query는 도메인 이름을 완전히 확인하거나 사용자에게 도메인을 찾을 수 없음을 알리는 오류 메시지를 반환합니다.

**Iterated Query**
![[Pasted image 20251209220148.png]]

Iterated Query는 Local DNS 서버와 비로컬 DNS 서버를 연결하는 쿼리로 도메인 확인이 필요하지 않습니다. 대신 서버는 조회로 응답할 수 있으며 여기서 루트 서버는 Local DNS 서버에 TLD로 참조하고 TLD는 권한 서버로 참조합니다. 따라서 Iterated Query는 답변 또는 참조로 해결됩니다.

**비재귀적 쿼리**  
비재귀적 쿼리의 경우 Local DNS Server는 쿼리에 대한 IP주소를 바로 찾을 수 있는 Authoritative DNS Server의 위치를 알고 있으므로 Local DNS Server는 캐시에서 응답을 찾거나 Root, TLD DNS Server를 건너뛰고 바로 Authoritative DNS Server로 쿼리하여 시간을 절역합니다.

만약 Local DNS Server가 이전 쿼리에서 캐시된 IP주소를 제공하는 경우 해당 요청은 비재귀 쿼리에 해당합니다.

### 3.6 DNS 보안
**DNS 스푸핑**  
캐시 포이즈닝이라고도하며 공격자가 Local DNS Server에 캐시에 잘못된 주소 레코드를 삽입하여 서버가 잘못된 IP주소를 반환하고 사용자를 악성 사이트로 리디렉션할 때 발생합니다.

**DDoS 공격**  
공격자가 피해자의 IP주소로 스푸핑된 반환 주소를 사용하여 DNS 서버에 작은 쿼리를 보내는 공격입니다.

**DNS 터널링**  
DNS 쿼리 및 응답에서 HTTP와 같은 비 DNS 트래픽을 캡슐화하여 보안 조치를 우회하는 기술입니다. 공격자는 DNS 터널을 사용하여 맬웨어 명령을 전달하거나 손상된 네트워크 데이터를 유출할 수 있습니다. 탐지를 피하기 위해 DNS 쿼리 및 응답 내에 페이로드를 인코딩하는 경우가 많습니다.

**도메인 하이재킹**  
도메인 하이재킹은 공격자가 도메인 등록 기관 계정에 무단으로 엑세스하여 도메인 등록 세부 정보를 변경할 때 발생합니다. 하이재킹을 통해 공격자는 트래픽을 악성 서버로 리디렉션하고, 이메일을 가로채고, 사용자의 온라인 ID를 제어할 수 있습니다.

**하위 도메인 탈취**  
사용 중지된 서비스를 가리키는 하위 도메인의 방치된 DNS 항목은 공격자의 주요 표적이 됩니다. 클라우드 호스트와 같은 서비스가 사용 중지되었지만 DNS 항목이 남아 있는 경우 공격자는 잠재적으로 하위 도메인을 요청하고 그 자리에 악성 사이트나 서비스를 설정할 수 있습니다.
