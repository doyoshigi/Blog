# TCP와 UDP의 특징 및 차이점
## 1. TCP 헤더구조
![[Pasted image 20251209205859.png]]

TCP 헤더는 여러 개의 필드로 구성되어 있습니다. 또한 TCP Header는 기본적으로 20byte의 크기를 가지며 옵션을 포함하면 최대 60byte까지 늘어날 수 있습니다.

참고로 TCP프로토콜의 전송 단위는 Segment입니다.

위의 그림을 참고하여 각 필드에 대해서 알아보도록 하겠습니다.

### Source Port, Destination Port
![[Pasted image 20251209205930.png]]

Source/Destination Port는 각각 출발지의 프로세스를 식별할 수 있는 포트 번호와 목적지의 프로세스를 식별할 수 있는 포트 번호를 나타냅니다.

길이는 각각 16bit로 총 32bit 크기입니다.

TCP/IP에서 컴퓨터 내 프로세스를 IP주소와 포트 번호를 통해 식별할 수 있습니다. 이를 위해 Transport 계층에서 포트 번호가 추가되며 Network 계층에서 IP주소가 추가됩니다.

### Sequence Number
![[Pasted image 20251209205943.png]]

Sequence Number는 segment의 byte stream에 1byte단위로 부여되는 숫자입니다.

그리고 segment의 byte stream의 순서를 의미하며 크기는 32bit입니다.

segment의 byte stream을 전송하면서 byte stream의 순서 중 가장 첫 byte의 sequence number가  표시됩니다.  
(만약 0~100byte까지 전송한다면 seq# == 0, 101~200byte까지 전송한다면 seq# == 101)

시퀀스 번호를 통해 수신자는 부분부분 전송되는 세그먼트의 순서를 배열하여 올바른 순서로 데이터를 수신할 수 있습니다.

송신자의 최초 데이터 전송 시에는 시퀀스 번호가 랜덤한 수로 초기화되며 자신의 보낼 데이터의 1byte당 번호를 1씩 증가시키며 데이터의 순서를 표현합니다. TCP는 양방향 통신이므로 서로 다른 시퀀스 번호가 사용됩니다.

값이 계속 증가해 범위(0~4,294,967,295)를 초과하는 경우 다시 0부터 시작합니다.

### Acknowledgement Number
![[Pasted image 20251209210143.png]]

Acknowledgement Number는 데이터를 받은 수신자가 다음에 수신되기를 기대하는 바이트의 번호를 의미합니다. 크기는 32bit입니다.

이는 데이터 송신자자가 다음에 보내줘야하는 데이터의 시작점을 의미합니다.

Acknowledgement Number는수신자가 수신한 byte stream의 마지막 sequence number + 1로 계산할 수 있습니다.

![[Pasted image 20251209210154.png]]

핸드 쉐이크 과정에서는 상대방이 보낸 sequence number + 1 로 계산됩니다.

### Data Offset
![[Pasted image 20251209210228.png]]

Data Offset은 전체 세그먼트 중에서 TCP헤더를 제외한 데이터가 어디에서 시작되는지를 표시합니다. 즉 TCP헤더의 길이를 나타내는 것 입니다. 크기는 4bits입니다.

이러한 필드가 필요한 이유는 TCP헤더의 길이가 Options 필드 때문에 가변적이기 때문입니다.

아까 초반에 언급 했듯이 헤더의 길이는 20바이트부터 60바이트까지 늘어날 수 있습니다. 이 필드의 단위는 32비트 word(1word = 4byte)단위 이므로 총 0~60byte까지 헤더의 길이를 표현할 수 있습니다.

### Reserved
![[Pasted image 20251209210254.png]]

Reserved 필드는 나중을 위해서 0으로 초기화되어있어야 하는 필드입니다. 크기는 4bits로 과거 2003~2017년도에 마지막 비트가 NS 플래그로 사용되었던 적이 있습니다.

### Flags
![[Pasted image 20251209210311.png]]

8개의 플래그를 나타내는 필드이며 크기는 8bits입니다.

**CWR**  
Congestion Window Reduced 플래그로 ECE 플래그를 받고 전송하는 세그먼트 윈도우 사이즈를 줄였다는 것을 나타냅니다.

**ECE**  
ECN Echo 플래그로 ECE 플래그와 SYN 플래그가 1일 때에는 ECN을 사용한다고 상대방에게 알려줍니다.  
SYN가 0이라면 네트워크가 혼잡하여 세그먼트 윈도우의 크기를 줄여달라는 요청의 의미입니다.

여기서 ECN이란 Explicit Congestion Notification으로 송신자와 수신자에게 네트워크의 혼잡 상황을 알리기 위해 사용하는 방법이며 CWR과 ECE 플래그가 이를 위해 사용됩니다.

**URG**  
Urgent Pointer필드에 값이 채워져 있음을 알리는 플래그로 Urgent Pointer가 가리키는 데이터는 우선적으로 처리됩니다.

**ACK**  
Acknowledgement Number 필드에 값이 채워져 있음을 알리는 플래그입니다. 만약 0이라면 Acknowledgement Number필드는 무시됩니다.

**PSH**  
Push 플래그로 수신 측에게 이 데이터를 최대한 빠르게 응용프로그램에게 전달해달라는 플래그입니다. 만약 0이라면 수신자는 자신의 버퍼가 다 채워질 때까지 기다리게 됩니다.

만약 이 플래그가 1이라면 지금 수신된 세그먼트 이후에 더 이상 추가적인 세그먼트가 없다는 것을 의미합니다.

**RST**  
Reset 플래그로 값이 1이라면 연결 상태가 ESTABLISHED 상태인 상대에게 연결을 강제로 리셋해달라는 요청을 의미합니다.

**SYN**  
Synchronize 플래그로 상대방과 연결을 생성할 때 현재 세그먼트가 시퀀스 번호를 동기화 하기 위한 세그먼트임을 의미합니다.

**FIN**  
Finish 플래그로 연결 종료를 표시할 수 있습니다.

### Window
![[Pasted image 20251209210343.png]]

Window 필드는 16bits크기의 필드로 수신자가 받을 수 있는 데이터의 바이트 크기를(receive window사이즈) 의미합니다.

### Checksum
![[Pasted image 20251209210406.png]]

Checksum 필드는 데이터를 송신할 때 발생할 수 있는 오류를 검출하기 위해 사용됩니다.

![[Pasted image 20251209210447.png]]

Checksum은 전송할 데이터를 16bits씩 나눠서 하나씩 더해갑니다. 하지만 그냥더하는 것은 아닙니다.

예를 들어 2개의 정수를 더한다고 했을 때 그 결과에서 Carry bit가 발생하면 이를 Carry를 제외한 부분에 더해줍니다.

이런 방식으로 전송할 데이터를 모두 더한 값의 1의 보수가 바로 checksum입니다.

송신측에서 이렇게 계산한 checksum과 수신측에서 수신한 데이터를 바탕으로 계산한 sum을 더해주어서 나온 값에서 모든 비트가 1이라면 데이터가 정상이라고 판단할 수 있습니다.

### Urgent Pointer
![[Pasted image 20251209210534.png]]

URG 플래그가 1이라면 수신측은 이 필드가 가리키고 있는 데이터를 우선적으로 처리하게 됩니다.

### Options
![[Pasted image 20251209210549.png]]

옵션 필드는 TCP의 옵션을 사용하기 위해서 설정되는 필드이며 크기가 가변적인 필드입니다. 따라서 이 필드의 가변성 때문에 TCP헤더의 길이를 정확하게 파악하기 위한 Data Offset 필드가 필요한 것입니다.

옵션으로는 윈도우 사이즈의 최대 값 표현을 확장할 수 있는 WSCALE, Selective Repeat 방식을 사용하기 위한 SACK등의 옵션이 있습니다.

만약 아무 옵션도 사용하지 않고 있더라도 Data Offset필드에 헤더의 길이가 30바이트로 표시되어 있다면 옵션 필드를 0으로 채워서 그 길이를 맞춰줘야 할 것입니다.

## 2. TCP 연결 방식: 3-way Handshaking
TCP에서는 데이터 수신자와 송신자 사이에서 데이터를 주고받기 전에 먼저 연결을 한 후 데이터를 전송하는데 이를 'handshake'라고 합니다.

handshake 과정에서는 송수신자 사이에 서로 연결할 의사가 있는지 확인하고 seq#와 같은 연결을 위해 필요한 파라미터를 결정합니다. handshake가 완료되었을 때에는 서로 데이터를 전송할 준비가 되어 있다는 것이 보장되어야 합니다.

### 2-way는 불가능한가?
![[Pasted image 20251209210742.png]]

그렇다면 위의 그림처럼 2-way로 handshake를 진행하면 안될까요? 왜 굳이 3-way shanshake를 진행할 까요?

![[Pasted image 20251209210833.png]]

만약 위와 같이 클라이언트에서 서버에 연결 요청을 보내고 서버에서 연결을 받아들인 후 이를 확인하는 메시지를 보냈는데 전송 속도와 같은 모종의 문제로 클라이언트는 이를 확인할 수 없게 된다면, 클라이언트는 다시 연결 요청을 보내겠죠.

그런데 다시 보내진 연결 요청을 서버가 아까 열렸었던 연결 x에 대한 연결이 끝난 후에나 이를 받을 수 있다면 연결 x에 대한 존재를 서버는 모르고 클라이언트만 알고 있는 이상한 상황이 발생하게 되는 것이죠.

이러한 현상을 방지하기 위해서 3-way handshake를 하는 것 입니다.

### 3-way handshake
![[Pasted image 20251209210900.png]]

1 - 먼저 클라이언트가 SYN 플래그의 비트를 1로 설정하고 seq#를 설정하여 통신하고 싶은 서버로 SYN 메시지를 전송합니다.

2 - 서버는 이를 확인하고 클라이언트에게 요청을 수락한다는 의미로 ACK, SYN 플래그를 1로 설정하고 seq#와 ack#를 설정하여 SYNACK 메세지를 다시 클라이언트로 전송합니다. 이때 ack num은 클라이언트로부터 수신한 seq num + 1입니다.

3 - 서버로부터 SYNACK 메세지를 받은 클라이언트는 이를통해 서버가 통신의 의지가 있다는 것을 확인하고 이에대한 ACK 플래그를 1로 설정하고 ack num을 설정하여 ACK 메세지를 전송합니다. 이때 ack num은 서버로부터 수신한 SYNACK 메세지의 seq num + 1입니다.

이로부터 서버는 클라이언트로부터 ACK 메시지를 받고 클라이언트가 통신의 의지가 있다는 것을 확인할 수 있습니다.

이러한 과정을 통해 TCP 연결이 수립됩니다.

### TCP 연결 종료
![[Pasted image 20251209211213.png]]

연결을 종료하는 것은 비교적 간단합니다.

먼저 TCP연결을 종료하고 싶어하는 클라이언트가 FIN 플래그를 1로 세팅한 세그먼트를 서버에 전송합니다.

FIN Segment를 받은 서버는 이에 확인했다는 ACK Segment를 전송합니다.

그 후 서버는 FIN Segment를 클라이언트로 전송합니다.

마지막으로 FIN Segment를 받은 클라이언트는 서버에게 확인했다는 의미로 ACK Segment를 전송하고 TCP 연결은 종료됩니다. 이 시점에서 해당 TCP연결에 관한 두 호스트의 리소스는 모두 해제되게 됩니다.

TIME_WAIT 상태는 보통 30초 정도로 클라이언트가 보낸 ACK Segment가 유실되었을 경우 그 ACK Segment를 재전송할 수 있도록 하는 시간입니다.

그 시간 안에 ACK Segment가 유실되었다면 재전송하며 TIME_WAIT이 끝난 이후에 클라이언트 쪽에 있는 리소스가 모두 할당 해제됩니다.

## 3. TCP 재전송 (타임아웃)
TCP 통신을 할 때 서버에서 데이터를 받아야하는 상황에서 데이터가 세그먼트 단위로 나뉘어서 전송되게 됩니다.

데이터가 전송되는 과정에서 문제가 발생하여 전송받지 못한 세그먼트가 생긴다면 어떻게 할까요?

![[Pasted image 20251209211433.png]]

데이터가 정상적으로 처리될 때에는 보낸 세그먼트에 대해서 수신자로부터 ACK을 받고 송신자는 이를 바탕으로 데이터가 정상적으로 잘 전달되고 있구나를 판단하게 됩니다.

![[Pasted image 20251209211441.png]]

하지만 위의 그림처럼 서버가 전송하는 세그먼트가 유실되면 클라이언트는 이를 받지 못하고 결과적으로 그에대한 ACK도 보내지 못하겠죠?

이때 서버에서는 일정시간동안 전송한 세그먼트에 대한 ACK이 수신되지 않는다면(타임아웃) 제대로 데이터가 전송되지 못했다고 판단하여 다시 그 세그먼트를 재전송하게 됩니다.

![[Pasted image 20251209211451.png]]

이런 경우도 생각해볼 수 있죠. 서버에서 전송한 세그먼트는 제대로 전달되었지만 클라이언트가 전송한 ACK이 유실된 경우 서버는 세그먼트가 잘 전달된지 알 수 없죠. 그래서 그 경우에도 타임아웃이 발생하여 해당 세그먼트를 재전송하게 됩니다.

### 타임아웃 시간 설정
![[Pasted image 20251209211510.png]]

그렇다면 타임아웃에 사용되는 시간은 어떻게 설정해야 할까요?

만약 타임아웃의 간격이 너무 짧다면 서버에서 보낸 세그먼트에 대한 클라이언트의 ACK이 정상적으로 도달하기도 전에 타임아웃이 발생하여 해당 세그먼트를 재전송하는 경우가 발생할 수 있습니다.

그리고 간격이 너무 길다면 세그먼트가 유실되었을 때 그 대처가 늦어져 전체적인 전송 속도에 영향을 주겠죠.

그래서 `Timeout Interval`을 설정할 때에는 과거의 기록으로 Rount Trip Time을 계산하는 `EstimatedRTT`와 그 마진인 `DevRTT` 를 사용합니다.  
**타임아웃 시간 = EstimatedRTT + 4*DevRTT**

## 4. UDP의 헤더구조
![[Pasted image 20251209211527.png]]

UDP헤더는 TCP 헤더와 달리 8bytes의 고정 크기를 가지고 있습니다. 따라서 헤더를 빠르게 처리할 수 있습니다.

UDP 프로토콜의 전송 단위는 Datagram입니다.

### Source Port, Destination Port
TCP의 필드와 마찬가지로 16비트의 포트 번호를 출발지/목적지를 표시하기 위해 사용합니다.

### Length
Length 필드는 UDP Header를 포함한 UDP Datagram의 전체 길이를 나타내는 필드입니다. 필드의 크기는 16bit이며 이 필드가 표시하는 단위는 바이트 단위입니다.(값이 10이라면 전체 데이터그램의 크기는 10바이트)

### Checksum
TCP 헤더의 Checksum과 같은 방식으로 작동한다.

TCP에서는 에러 검출을 위해 Checksum 필드를 무조건 사용해야 하지만 하지만 UDP에서 성능을위해서 Checksum필드를 사용하지 않을 수도 있습니다.(사용하지 않을 때에는 필드에 0을 할당)

### UDP 통신 방식
UDP는 TCP처럼 handshake를 통해 연결을 수립할 필요가 없고 Sequence number가 없어 ACK을 확인할 수도, 순서를 제어하여 보낼 수도 없으며 혼잡 제어나 오류 제어와 같은 기능도 없어서 Application layer에 의존해야 하는 매우 단순하지만 속도가 빠른 프로토콜 입니다.

신뢰성은 낮지만 속도가 빨라 실시간 스트리밍처럼 빠르게 데이터를 전송해야 하는 상황에 적합합니다.
