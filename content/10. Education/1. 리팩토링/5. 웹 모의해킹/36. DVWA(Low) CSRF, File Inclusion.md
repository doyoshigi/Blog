## 실습 환경
![[Pasted image 20251212205942.png]]

칼리 리눅스에 DVWA를 설치하여 Security Level을 Low로 설정했습니다.

## CSRF
### CSRF란?
CSRF(Cross-Site Request Forgery, 사이트 간 요청 위조)란 로그인 등 인증이 되어 있는 사용자의 권한을 악용하여 공격자가 사용자의 의지와 무관하게 웹사이트에 원치 않는 요청을 실행하게 하는 공격 기법입니다.

서버가 사용자의 브라우저에 저장된 세션이나 쿠키를 신뢰하는 점을 악용하는 공격입니다.

CSRF 공격이 발생하면 서버의 입장에서는 피해자가 공격자처럼 보이게 됩니다.

### CSRF 공격 방식
![[Pasted image 20251212210015.png]]

1. 사용자가 이미 로그인한 상태에서 공격자가 조작한 피싱 사이트, 이메일 링크, 광고 등을 클릭하게 유도합니다.
2. 사용자가 해당 링크를 클릭하면 사용자의 브라우저가 자동으로 사용자가 인증한 웹사이트에 악의적인 요청을 전송합니다.
3. 요청에는 사용자의 세션 쿠키가 자동으로 포함되므로, 서버에서는 이를 정상적인 사용자 요청으로 오인하게 됩니다.
4. 이를 통해 공격자는 사용자의 계정으로 데이터 변경, 삭제, 송금 등 피해자의 의도와 다른 작업을 실행시킬 수 있습니다.

### CSRF 3요소
CSRF 공격을 위해 만족되어야 할 요소는 아래와 같습니다.
- 공격자가 유도할 이유가 있는 동작이 존재해야 합니다.(사용자 비밀번호 변경, 계정 권한 수정 등)
- 해당 동작을 수행하기 위해 하나 이상의 HTTP/HTTPS 요청이 발생하며, 애플리케이션은 요청을 보낸 사용자를 식별하는 데 오직 세션 쿠키만을 사용해야 합니다.
- 해당 동작을 수행하는 요청에는 공격자가 알 수 없거나 예측할 수 없는 파라미터가 포함되어 있으면 안됩니다.
    - 예를 들면 계정 비밀번호를 변경할 때 기존 비밀번호를 알아야 한다면 공격할 수 없습니다. 예측하지 않는 이상 공격자가 알아낼 수 없기 때문입니다.

### CSRF 실습
![[Pasted image 20251212210041.png]]

DVWA 실습 페이지의 왼쪽 탭에서 'CSRF' 탭을 눌러보면 비밀번호를 변경할 수 있는 페이지가 나옵니다.

![[Pasted image 20251212210047.png]]

여기서 1234로 비밀번호 변경을 요청하고 해당 패킷을 Burp Suite 프록시로 확인한 모습입니다.

서버에 GET 요청을 보내 비밀번호를 변경하고 있는 것을 확인할 수 있습니다.

이를 참고하여 비밀번호를 변경하는 하이퍼 링크를 만들어보면

[`http://localhost/DVWA/vulnerabilities/csrf/?password_new=1234&password_conf=1234&Change=Change`](http://localhost/DVWA/vulnerabilities/csrf/?password_new=1234&password_conf=1234&Change=Change)
와 같습니다.

사용자가 로그인을 한 후 위의 링크를 클릭하게 되면 사용자의 비밀번호를 1234로 변경시킬 것입니다.

![[Pasted image 20251212210300.png]]

사용자가 해당 링크를 클릭한다는 가정하에 브라우저를 통해 만든 링크로 접속하면 CSRF 페이지로 이동되며 위 사진처럼 "Password Changed."라는 메시지가 떠 있는 것을 확인할 수 있습니다.

![[Pasted image 20251212210307.png]]

다시 로그인을 시도해보면 기존 비밀번호로 로그인에 실패하며 1234로 해야 로그인되어 비밀번호가 성공적으로 1234로 변경된 것을 확인했습니다.

이와 같은 링키를 웹사이트의 글, 이메일 등에 삽입하여 CSRF 공격을 할 수 있습니다.

이 글에서는 링크로 이동하면 "Password Changed." 메시지가 보이는 비밀번호 변경 페이지로 이동하기 때문에 `<img src=[변조된 링크]>` 등과 같이 클릭하여도 리디렉션이 일어나지 않게 한다면 피해자가 피해 사실을 쉽게 인지하지 못할 것입니다.

### 대응방안
- 토큰 기반 인증(JWT, OAuth2 등)을 사용합니다.
- 중요한 요청은 CAPTCHA를 요구합니다.
- 쿠키의 `SameSite` 속성을 `Strict` 혹은 `Lax`로 설정하여 외부 사이트에서 오는 요청에는 인증 쿠키가 첨부되지 않도록 제한합니다.
- Referer, Origin 헤더 검증을 통해 사용자의 요청이 신뢰하는 도메인에서 온 경우만 요청을 허용합니다.

최근에는 토큰 기반 인증이 확산되고, CORS(Cross-Origin Resource Sharing) 정책이 강화되는 등의 보안이 강화되어 CSRF 공격을 성공하기 힘들어졌습니다. 하지만 여전히 레거시 시스템에게는 치명적일 수 있습니다.

## File Inclusion
### File Inclusion이란?
File Inclusion(파일 포함) 취약점이란, 웹 애플리케이션이 외부 또는 내부 파일을 사용자 입력값을 바탕으로 동적으로 불러와 실행할 때 적절한 검증이 이루어지지 않아, 공격자가 임의의 파일(악성코드 등)을 서버에서 불러오거나 실행할 수 있는 보안 취약점을 말합니다.

주된 원인은 include, require 등 파일을 불러오는 함수에 입력값 필터링이 부족할 때 발생합니다.

File Inclusion에는 두 가지 유형이 있습니다.
- **RFI**(Remote File Inclusion): 공격자가 **외부 서버**에 존재하는 악성 파일(웹 쉘 등)을 URL 파라미터에 포함시켜 원격에서 불러와 실행하는 취약점입니다.
- **LFI**(Local File Inclusion): 공격자가 **서버 내부**에 존재하는 파일을 불러오거나 실행하게 하는 취약점입니다.

### File Inclusion 실습
#### 소스코드 분석
![[Pasted image 20251212210452.png]]

DVWA의 왼쪽 항목에서 'File Inclusion' 탭으로 이동해보면 URL에 `page=include.php`라는 쿼리 파라미터를 확인할 수 있습니다.

![[Pasted image 20251212210500.png]]

File Inclusion 페이지의 소스코드를 DVWA에서 확인해보면 파라미터를 통해 아까 URL에서 살펴보았던 page의 값이 `$file`에 저장되는 것을 확인할 수 있습니다.

![[Pasted image 20251212210510.png]]

아직 정보가 부족하기에 URL을 참고하여 `/var/www/html/DVWA/vulnerabilities/fi/index.php`파일을 살펴보면

사용자가 일정한 난이도의 파일을 index.php 본문에서 실행하는 것을 확인할 수 있습니다.

또한 `$file` 값이 null이라면 '현재주소/?page=include.php`로 리디렉션을 하고 null이 아니라면` $file`에 저장되어 있는 값을 현재 스크립트에 include합니다.

![[Pasted image 20251212210523.png]]

지금까지 모은 정보를 취합해보면 32번째 줄에서 위에서 봤던 `low.php`의 `$file = $_GET['page'];`가 실행되고

따라서 `$file`에 입력된 값이 `index.php`에 include 될 것입니다. 

#### LFI(Local File Inclusion) 실습
![[Pasted image 20251212210536.png]]

공격자가 악성 파일을 이미 서버에 업로드 해 놓은 상황을 설정하기 위해 스크립트 파일을 Apache 서버의 웹 루트 디렉토리인 `/var/www/html`에 만들겠습니다.

![[Pasted image 20251212210544.png]]

스크립트 파일에는 File Inclusion 발생을 알릴 수 있는 구문을 프린트하고 리눅스의 사용자 계정 정보 파일을 출력하도록 했습니다.

![[Pasted image 20251212210551.png]]

스크립트 파일이 웹 루트 디렉토리에 존재하기 때문에 파라미터에 `http://localhost/fi_test.php`를 입력하여도 동일하게 실행되는 것을 확인할 수 있습니다.

![[Pasted image 20251212210558.png]]

파라미터에 외부 서버 URL을 입력해도 잘 include 되는 것을 볼 수 있습니다. 이를 이용하여 악성 스크립트를 외부 서버에 저장해놓고 해당 URL을 정상적인 URL에 포함시켜 공격할 수 있습니다.

## 대응방안
- 사용자가 입력하는 파일명과 경로에 대해 화이트리스트 기반 검증을 수행합니다.
- '../', '..', '/', '\' 등의 경로 이동을 할 수 있는 특수문자와 파일 확장자 우회를 막는 특수문자를 필터링합니다.
- 서버 설정에서 File Inclusion을 발생시킬 수 있는 설정을 제거합니다.
    - PHP의 경우 `allow_url_fopen`과 `allow_url_include`를 'Off'로 지정하여 막을 수 있습니다.
    - 또한 `display_error`를 'Off'로 설정하여 취약점 공격과 실패 시 내부 구조 노출을 방지할 수 있습니다.
- 미들웨어나 내부 로직을 통해 허용한 파일만 include될 수 있도록 합니다.
- include, require 등 파일 불러오기 구문을 동적으로 사용하지 않거나 사용한다면 반드시 입력값 검증과 경로 제한을 적용합니다.

서버의 설정을 끄면 근본적인 해결이 가능하지만 해당 기능을 막음으로서 서비스의 효율성이 감소한다면 필터링과 같은 방법을 적용하여 사용해야 합니다.
