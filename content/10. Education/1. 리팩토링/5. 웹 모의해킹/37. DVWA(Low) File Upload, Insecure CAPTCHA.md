# DVWA(Low) File Upload, Insecure CAPTCHA
## 실습 환경
![[Pasted image 20251212205942.png]]

칼리 리눅스에 DVWA를 설치하여 Security Level을 Low로 설정했습니다.

## File Upload 취약점이란?
![[Pasted image 20251230204313.png]]

파일 업로드 취약점이란 웹 서비스의 파일 업로드 기능을 통해 공격자가 웹쉘 등의 악성 파일을 서버에 업로드해 서버를 장악하거나, 시스템에 명령을 내릴 수 있는 취약점을 말합니다. 

업로드된 파일의 확장자를 검증하지 않거나, 검증하더라도 확장자 우회를 허용하는 경우, 업로드된 파일의 저장 경로에 실행 권한이 있거나 경로가 노출되는 경우, 파일의 내용이나 크기, 타입에 대한 검증이 이루어 지지 않는 경우 등에 발생합니다.

## 대응방안
- 업로드 디렉토리가 노출되지 않도록 합니다.
- 업로드 디렉토리의 실행 권한을 최소한으로 설정합니다.
- 파일의 내부 구조, 확장자, 크기, 헤더 정보 등을 검증하여 악성 파일이 업로드되지 않도록 합니다.
- 업로드된 파일의 경로나 파일명을 예측되지 않도록 랜덤값으로 설정하여 경로를 파악하여 파일을 실행하지 못하도록 합니다.

**CAPTCHA란?**
![[Pasted image 20251230204455.png]]

CAPTCHA(Completely Automated Public Turing test to tell Computers and Humans Apart)란 웹 사이트나 온라인 서비스에서 사람과 자동화된 봇을 구분하기 위해 사용하는 자동화된 챌린지-응답(Challenge-Response) 시스템입니다.

사용자가 봇이 아닌 실제 인간임을 증명하도록 왜곡된 문자 입력, 특정 이미지 선택 등의 문제를 제시하고 이를 올바르게 풀면 서비스 시용이 가능합니다.

## Insecure CAPTCHA란?
Insecure CAPTCHA 취약점이란 웹 서비스가 봇 공격 방지 기능으로 사용하는 CAPTCHA 시스템에 충분한 보안이 적용되지 않아 자동화된 공격이나 우회 수법에 쉽게 뚫릴 수 있는 상태를 뜻합니다.

몇가지 케이스를 예로 들어보면

- 이미지를 선택하는 인증방식의 경우 OCR(Optical Character Recognition, 광학 문자 인식) 기술을 사용하여 텍스트를 인식하고 해독할 수 있습니다.
- 정답값이 고정되거나 예측 가능한 패턴을 따르는 경우나, 설계가 불완전한 인증 방식을 사용할 경우 취약점이 발생할 수 있습니다.

## Insecure CAPTCHA 실습
![[Pasted image 20251230204517.png]]

DVWA 페이지에서 'Insecure CAPTCHA'탭으로 이동하면 비밀번호를 변경할 수 있는 입력창과 CAPTCHA가 있는 것을 확인할 수 있습니다.

![[Pasted image 20251230204526.png]]

변경할 비밀번호를 입력하고 CAPTCHA 인증 후 변경 요청 패킷을 프록시로 잡아서 확인해보면 입력한 비밀번호와 그 앞에 `step=1`라는 값을 확인해볼 수 있습니다.

![[Pasted image 20251230204535.png]]

잡아둔 패킷을 Forward시키고 다시 페이지를 확인해보면 캡차를 통과했으니 아래의 버튼을 눌러서 비밀번호 변경을 확정하라는 문구를 볼 수 있습니다.

![[Pasted image 20251230204541.png]]

`Change` 버튼을 클릭 후 캡처한 패킷을 확인해보면 아까 1이었던 `step`값이 2로 변경된 것을 확인할 수 있습니다.

![[Pasted image 20251230204548.png]]

그리고 이 패킷을 Forward하고 다시 페이지를 확인해보면 비밀번호가 변경되었다는 문구를 확인할 수 있습니다.

다시 로그인해보면 비밀번호가 `1234`로 정상적으로 변경된 것을 확인할 수 있습니다.

![[Pasted image 20251230204556.png]]

이 동작을 보면 `step` 값이 2일 때 비밀번호가 변경되는 것이라고 예상해볼 수 있습니다. 이를 시험해보기 위해서 `step`값이 2인 패킷을 burp suite의 Repeater로 보냅니다.

![[Pasted image 20251230204605.png]]

패킷의 비밀번호를 1234에서 1111로 수정하고 전송해보았을 때 아까와 마찬가지로 비밀번호가 변경되었다는 문구를 확인할 수 있었습니다.

![[Pasted image 20251230204612.png]]

step값을 1로 바꾸고 보내보면 캡차 인증이 틀렸다는 구문이 나옵니다.

따라서 처음 페이지에서 비밀번호를 변경할 때 step값을 2로 변경하고 시도한다면 캡차 인증을 통과하지 않아도 비밀번호를 변경할 수 있을 것입니다.

![[Pasted image 20251230204620.png]]
![[Pasted image 20251230204634.png]]

다시 처음 페이지에서 비밀번호 변경을 시도하고 step값을 2로 수정하고 Forward시켰습니다.

![[Pasted image 20251230204639.png]]

그러면 이전과는 다르게 바로 비밀번호가 변경되었습니다 라는 문구가 나오는 것을 확인할 수 있습니다.

다시 로그인을 해보면 캡차를 하지 않았음에도 설정한 비밀번호로 로그인이 되는 것을 확인할 수 있었습니다.

### Insecure CAPTCHA 소스코드
![[Pasted image 20251230204646.png]]

페이지의 소스코드를 살펴보면 `step`값이 1일 대에만 캡차 검증을 하고

![[Pasted image 20251230204652.png]]

2일 때에는 바로 서버에 반영하는 것을 확인할 수 있습니다.

따라서 패킷의 step값을 바꾸는 것만으로 캡차 인증을 우회할 수 있는 것입니다.

## 대응방안

- CAPTCHA 정답 검증은 서버에서 수행되어야 합니다.
- 인증 요청마다 새로운 CAPTCHA 값을 생성하고, 세션 단위로 관리해 이전 값을 재사용하지 못하도록 만듭니다.
- 같은 IP나 세션에서 반복적인 CAPTCHA 인증을 시도할 시 동작에 일시적인 제한을 둡니다.
- 캡차에 단독으로 의존하지 않고 CSRF 토큰, 레이트리밋/락아웃, 비밀번호 재확인 등의 다중 인증을 사용합니다.
