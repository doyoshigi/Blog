# AWS 기초 환경 구성 및 이해
![[Pasted image 20251214151300.png]]

구성한 환경에 대한 다이어그램이다.

## VPC
![[Pasted image 20251214151324.png]]

10.0.0.0/16 대역의 커스텀 VPC를 생성하고 내부의 10.0.1.0/24 대역을 Public Subnet으로 구성했다.

그리고 인터넷 게이트웨이를 생성하고 라우팅테이블을 생성하여 퍼블릭 서브넷의 아웃바운드 트래픽이 인터넷으로 라우팅되도록 설정했다.

### NACL
![[Pasted image 20251214151349.png]]

규칙번호 90번을 보면 특정 IP(1.2.3.4/24)를 차단해놓았는데 이는 특정 해커나 악성 봇의 IP를 가정하고 차단해 놓았다.

퍼블릭 서브넷 내부의 웹 서버로 인터넷으로부터의 요청이 잘 전달되도록 HTTP(80)포트를 허용해 놓았다.

NACL은 Stateless이기에 EC2에서 외부 인터넷으로 요청한 트래픽에 대한 응답 트래픽이 다시 NACL를 거칠 때 이를 구분하지 못하고 인바운드 규칙이 적용된다. 따라서 응답 트래픽이 통과할 수 있도록 NACL 규칙을 구성해야 한다. 트래픽을 외부로 전송 시에 응답을 받을 포트를 임시포트(1024-65535)로 설정한다. 따라서 상대방은 임시포트 범위 중 하나의 포트로 다시 응답을 전송하게 되므로 TCP의 임시포트 트래픽을 허용하는 규칙을 추가했다. 이는 EC2가 인터넷과 통신할 때 응답 트래픽을 받기 위해서이다.

![[Pasted image 20251214151547.png]]

아웃바운드 규칙에서도 인바운드 때와 마찬가지로 사용자가 EC2 웹 서버에 트래픽을 요청한 후 EC2서버가 보낸 응답 트래픽을 통과시켜 사용자에게 전달하기 위해서 임시포트 범위의 트래픽을 허용했다.

또한 EC2 웹 서버가 프로그램 설치나 타 AWS 서비스와 통신하기 위해 HTTPS(443)와 HTTP(80)을 허용했다.

### Endpoint
웹 서버와 DB 역할인 S3 버킷 간 통신에서 인터넷이 아닌 AWS의 백본망을 통해 통신하기 위해 Endpoint를 생성하여 라우팅 테이블에 등록했다. 

### VPC Flow Log
vpc 내부의 트래픽을 S3에 저장되도록 설정했다.

## IAM
![[Pasted image 20251214151605.png]]

현재 EC2 웹 서버는 S3 버킷에 저장된 이미지 파일을 읽고 저장한 후 해당 파일을 웹 페이지로 출력해야 한다. 최소 권한 원칙에 따라 IAM Role을 구성하여 S3에 대한 읽기 권한을 부여하고  Systems Manager를 이용해 EC2 콘솔에 접근하기 위해 AmazonSSMManagedInstanceCore 권한을 부여했다.

## EC2
S3 버킷에 저장된 이미지 파일을 읽고 저장한 후 출력하는 간단한 웹 페이지 서비스하는 웹 서버이다. 생성한 커스텀 VPC의 퍼블릭 서브넷에 위치한다.

### Security Group
![[Pasted image 20251214151655.png]]

NACL과는 다르게 Security Group은 Stateful이기에 EC2 인스턴스에서 요청한 트래픽의 응답 트래픽이 Security Group에서는 룰에 상관없이 통과되게 된다. 아웃바운드 트래픽은 모두 허용해 놓았았으므로 인바운드 룰에서는 인터넷의 웹 서버에 관한 요청만 통과하도록 설정했다. 또한 키  쌍(.pem)을 사용하지 않고 SSM으로 EC2에 접근하므로 SSH(22)를 허용하지 않아도 된다.

## S3
EC2 웹 서버의 DB 용도로 S3 버킷을 생성하였다. EC2 웹 서버와 VPC 엔드포인트를 통해 통신한다.

### Bucket Policy
![[Pasted image 20251214151720.png]]

버킷 정책을 구성하여 설정한 VPC 엔드포인트를 경유한 트래픽과 루트 계정과 관리자 계정만 접근을 허용해 보안을 강화했다.
